# M6: delegation

**Status:** closed by the owner on 2026-10-23, after a coding job ran on the deployment from the clone to an opened pull request; steps not yet run on the deployment are carried into M7 (§8). The smoke test (§1) was written before the build (VISION rule 7), from the draft in [HANDOFF-M6.md §6](HANDOFF-M6.md#6-a-first-draft-of-m6s-smoke-test) and the owner's choices of 2026-10-23 (§4). §3 says what's built and §3a how to set it up; §5 has what was checked before building; §6 what building it found; §7 what the smoke test found. [HANDOFF-M7.md](HANDOFF-M7.md) has where M6 leaves things.

M6 proves **it runs your projects while you're away** (VISION §25). It adds:

- **coding jobs** (§8.2): a coding agent (Codex first, then Claude Code) run over ACP, the Agent Client Protocol, in the workspace container, on a branch of a GitHub repo;
- **Atlas as the middleman** (§8.2): it watches the job, answers routine questions from what it knows, brings the owner only real decisions, reviews the diff and the tests, and opens the pull request;
- **long jobs** (§8.1): helpers that run for hours with their own budget, survive a deploy, cost nothing while they wait on the owner, and report progress;
- **research jobs**: a helper that reads and compares for a long while and lands a research view and a page with sources.

**Exit:** the smoke test (§1) passes on the owner's deployment, then M5's carried steps and the earlier lists.

## 1. The smoke test

Run it on the owner's deployment after every deploy that touches the core, then the regression lists. When a line doesn't just work, the fix goes in the character, the context, a tool's description or the tool (rule 1), and the finding goes in this doc.

"The budget app" stands for one of the owner's real repos on GitHub with a failing test; use whichever fits.

**Setting up**
1. Settings → Extensions lists Codex and Claude Code as coding agents, each with the sites it reaches and what it needs. Codex uses the ChatGPT sign-in Atlas already has (Settings → Brains), with no second sign-in. Claude Code takes an Anthropic API key and a spending cap per job. Until the first job, neither installs anything in the workspace or costs anything.
2. The GitHub extension says which permissions its token needs for jobs (reading and writing the repo's contents and pull requests, on the repos the owner picks) and why. With a read-only token, a job still runs and stops before the push, in GitHub's own words.

**Coding jobs**
3. "Fix the failing test in my budget app" starts a job with Codex in the workspace, on a new branch. Atlas asks which repo only when it can't tell. The toolbar shows "1 job running"; Agenda lists it; Home → Jobs shows its steps (Plan, Edit, Test, PR), the agent's live terminal, and Steer and Stop.
4. The coding agent reaches only its own model's site, the repo, and the sites the owner allowed. A new one (a package registry, the first time) reaches the owner as an approval, like any workspace site, and is remembered after a yes. No key or token is ever inside the container: each is added at the gate.
5. The coding agent can't push, open a pull request or talk to anyone itself. A push from inside the container is refused at the gate, with a receipt naming the repo.
6. A routine question from the agent ("which test runner?") is answered by Atlas without the owner, from the repo, the project's area or the owner's preferences. Jobs lists each answer with its source. Edits and commands inside the job's folder are allowed without asking.
7. A real decision ("drop the old API or keep both?") reaches the owner as one question, in Inbox with a push, or on Telegram with buttons when that's where the owner is. The answer goes back into the session and the job carries on. While it waits, the job shows "waiting on you", and the container sleeps after its usual idle time instead of billing; the answer wakes it where it was.
8. Steer ("use the existing date helper instead") reaches the agent mid-run. Stop ends the job, keeps the branch, and says how far it got.
9. When the agent says it's done, Atlas reads the diff and runs the tests itself. If a test still fails or the diff does more than was asked, it sends the agent back with what's wrong, or tells the owner when that doesn't fix it. The diff and the test results show on the stage.
10. Atlas pushes the branch and opens a pull request through the GitHub extension, with a description of what changed and why. The receipt links to it, and the result is in Inbox. Atlas never merges.
11. "How's the budget app job?" by voice answers from the job's state: the step it's on, the last thing it did, what it's waiting on, and the time and money so far.
12. A deploy mid-run: the job carries on from where it was, in a new container with the same folder and branch, and Jobs says it restarted.
13. The same job with Claude Code works the same way, by Anthropic API key. At its spending cap it stops and says how far it got and what it cost.
14. A second job, on another repo, runs beside the first, each in its own folder, and neither sees the other's changes.

**Long jobs**
15. A job that runs past an hour isn't counted as lost while it's still working. A job whose agent hangs (no progress for its stall time) is ended as failed with the reason, and the owner hears about it once.

**Research**
16. "Research the best way to sync a SQLite database across devices; take your time" starts a research job. Jobs and Agenda show its progress (sources read, what it has so far), and "how's the research going?" answers from that. It survives a deploy mid-run.
17. It lands a research view on the stage and a page with its sources, and the result is in Inbox.

**Regression**
18. M5's carried steps ([M5.md §5b](M5.md#5b-carried-into-m6)): Gmail, Atlas's own email, Telegram, GitHub's and Linear's tokens, and step 8 after the next deploy. Then M4's ([M4.md §7](M4.md#7-carried-into-m5)).
19. M5's smoke test, then M4's, M3's, M2's, M1's and M0's.

## 2. The plan

From [HANDOFF-M6.md §4](HANDOFF-M6.md#4-m6-delegation), with the owner's choices (§4):

1. **Verify first** (§5): checked on 2026-10-23, apart from what needs the owner's deployment and accounts. The first slice of the build finishes them: Codex in the workspace answering one prompt on the owner's plan through the gate, then a deploy while it works.
2. **Groundwork:** run M5's carried steps with the owner and fix what they find.
3. **Long helpers:** a budget per job (time, steps, money) in place of the one `HELPER_BUDGET`; the job's lease renewed at each checkpoint, so it catches a stalled job instead of a long one (today it's fixed at 20 minutes from the start, `core/src/agent/helpers.ts`); waiting on the owner as a saved state that holds nothing open. Work inside a container doesn't count as activity, so while a job runs, its agenda item wakes every minute or so: one wake checks the job, renews its lease and touches the workspace, which keeps the container up (§5, item 3). There's no second timer.
4. **ACP in the core:** a client for the open standard (sessions, prompts, the update stream, permission requests, cancel, and loading a saved session), talking to the agent's process in the workspace over one stream the `Workspace` object holds. A small bridge in the container starts the agent and keeps it running when that stream drops (a deploy drops it, §5 item 3), holding what the agent says until the core reconnects. The agent's environment is built from nothing: only what Atlas sets, so it can't pick up a credential Atlas didn't mean to give it (§5, item 2). Nothing in it names an agent.
5. **Coding agents as extensions:** a coding agent is an extension that provides one (§17): its package and version, how to start its ACP server, the sites it reaches, how its model's address and a placeholder key are given to it, and its key or the core's sign-in. Codex first, then Claude Code.
6. **The gate adds a header per site,** named by what it guards, not always `authorization` (§5, items 1 and 4): a bearer token for `api.openai.com` and `api.github.com`, `x-api-key` for `api.anthropic.com`, and Basic for git at `github.com`.
7. **The coding job is a helper** (§8.1, `core/src/helper.ts`), not a second kind of background work: its tools are the ACP session plus the lookups it needs to answer questions. Permission requests inside the job's folder are allowed; anything else, and any real decision, goes to the owner through the outbox as a question or an approval.
8. **GitHub writes:** the GitHub extension gains what a code host provides (clone, push a branch, open a pull request), with its token added at the gate for Atlas's own git steps only. Opening a pull request is an `Action` kind with a receipt (`core/src/approvals.ts`, `Outbox.perform`).
9. **Jobs on the stage** (§21.4): steps, the terminal, questions answered with their sources, Steer and Stop; the diff and the tests through the code view.
10. **Research jobs:** a helper with the web tools and a long budget, with progress in Jobs and Agenda, ending in a research view and a page.
11. **Reviews:** three reviews of the whole change, by area, before the smoke test (HANDOFF-M6 §2). Anything the coding agent writes, and anything in the repo, is input from a stranger.

Keep the invariants: one loop, one log, one clock, one way out, one intake. Nothing tied to one service in the core.

## 3a. Deploying and setting up

1. Deploy as usual (`npm run deploy`). The workspace now starts at `standard-1` (half a vCPU, 4 GB); a container already running keeps its size until it next starts.
2. Settings → Extensions: install **GitHub** if it isn't, with a classic token that has the `notifications` and `repo` scopes (and `workflow` if jobs may change `.github/workflows`). Its Test says which account the token is.
3. Install **Codex** (it needs the ChatGPT sign-in in Settings → Brains) or **Claude Code** (it needs an Anthropic API key, and has a cap per job, $5 to start). With both, the one installed first is the default, and "with Claude Code" picks the other.
4. "Fix the failing test in my budget app" starts a job. The first one installs the agent in the workspace, which takes a minute.

## 4. Decisions

The owner's choices, 2026-10-23:

1. **Codex first, then Claude Code.** Codex runs on the owner's ChatGPT plan, through the sign-in Atlas already has. Claude Code runs by Anthropic API key, with a cap per job: what we found in October 2026 is that Anthropic points products built on Claude Code to API keys, and whether a Claude plan may power it inside Atlas is still unsettled (VISION §18).
2. **Jobs always run in the workspace container,** never on a node or the Mac. VISION §8.2 and §16.3 say so now.
3. **Repos come from GitHub,** through its extension, and Cloudflare Artifacts is left out of M6. Compared with GitHub and the workspace, it would add a second place work is saved, a copy in and out of each job (its import takes only public repos), and another token and bill, for gains the workspace already gives: a job's branch kept in R2 survives a deploy, and the GitHub token added at the gate only for Atlas's own git steps keeps the agent from pushing. It's for later: many forked attempts at one task, projects with no GitHub repo, or previews through Workers Builds.
4. **Atlas pushes and opens the pull request, not the coding agent,** after it has reviewed the diff and the tests. Opening a pull request on the owner's own repo is changing their own things in an undoable way (§12.1): Atlas does it and tells them. Merging stays the owner's.

Decided while building:

5. **A permission request inside the job's folder is a yes; outside it, a no.** The container is the sandbox and the gate decides what it can reach, so the owner is never asked to approve a command; they're asked real questions. Codex runs in its `agent` mode (it asks only about what looks unsafe), Claude Code in `acceptEdits`.
6. **Each turn's end is one short look, not one long helper for the whole job.** The job's state lives in the agent object, so waiting on the agent or the owner costs nothing and a look that's lost is simply started again.
7. **The workspace runs at `standard-1`.** The smallest size (256 MB) can't build real projects; this costs about $0.04 an hour while it runs, and it still sleeps after ten minutes unused.
8. **Agents are installed on first use after the container starts,** outside `/workspace` so they don't count against its copy (Codex's own binary pinned beside its adapter). Keeping them in a snapshot would save the download (Codex is about 450 MB) after each sleep; it's left for when that matters.
9. **The coding agent is treated as a stranger** (anything in a repo can steer it): it runs as the job's own user, which can't read the owner's files, other jobs, root's processes or the bridge's key. Atlas's own commands on its work run as that user too, so nothing the agent wrote (a test, a git hook or filter) runs as root, and the push copies the commit's objects out as data before any key is on the gate. Root never runs git inside the job's folder: the clone is made in a staging folder only root can reach, given to the job's user there and moved in. Three reviews of the change, and a fourth of the fixes, found how the first design let an agent reach git's token; this is what they led to.
11. **The owner's vault keys are off the workspace's gate while a coding job runs.** The gate can't tell which process is asking, so an agent could otherwise reach those sites with the owner's keys. The owner's own commands then reach those sites without their key, and say so; the keys are back once no job runs.
10. **The owner's words, a settled approval and Stop are written down at once and taken by the job's next wake,** so the owner never waits behind a long step, and a failure there is retried like any other.

## 5. Verify first

Questions whose answers change the build. Each was checked on 2026-10-23, with the real Codex and Claude Code adapters (`@agentclientprotocol/codex-acp` 2.2.2, which runs Codex 0.160, and `@agentclientprotocol/claude-agent-acp` 0.95.0) driven over ACP against fake model servers that recorded every request, and with Cloudflare's, OpenAI's and GitHub's docs. What's left needs the owner's deployment and accounts, and gets checked by the first slice of the build.

1. **Codex on the ChatGPT sign-in, from Cloudflare: yes, by design; one real request left.**
   - OpenAI documents exactly this: Codex with a model provider at `https://api.openai.com/v1`, the plan sign-in's token sent as `Authorization: Bearer`, and no separate Codex sign-in ([Codex app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)). Cloudflare's own Codex guide adds the token in the outbound Worker the same way ([Codex in a sandbox](https://developers.cloudflare.com/sandbox/coding-agents/codex/)).
   - The Codex adapter takes this over ACP: Atlas declares it can route a gateway at `initialize`, then authenticates with the `gateway` method, a base URL and headers. Codex then sent every request to that URL with the placeholder header Atlas gave it, with `store: false` and `stream: true` as OpenAI's plan route requires. It ran a command in the repo and answered.
   - Codex sends its tools as one `additional_tools` input item, grouped in namespaces (the plan route wants namespaces), including a freeform `exec` tool. Whether the plan route takes those shapes needs one real request with the owner's token. Atlas's own brain already reaches `api.openai.com` from Cloudflare with the same token, so the region isn't in question.
   - Codex's modes: `read-only`, `workspace-write`, `agent` (asks only for what looks unsafe) and `agent-full-access`. In `read-only` a command was quietly refused, not asked about, so which mode a job runs in, and how its asks reach Atlas, is checked in the build.
2. **ACP in the container: yes for both agents.**
   - Both adapters speak ACP over stdio, can load a saved session, and list sessions. Each was killed mid-session and started again: loading the session replayed it, and the next prompt carried the whole history. What makes that work is the agent's own folder (`CODEX_HOME`, about 4 MB, or Claude Code's config folder, under 200 KB), so a job keeps it beside its branch.
   - Claude Code asked permission over ACP before running a command (allow once or reject once), which is where Atlas answers as the middleman. It took its model's address and key from `ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY` and sent the key as `x-api-key`.
   - Started with the spike's own environment, Claude Code ignored the placeholder key and sent a sign-in token it found there. Hence the rule in §2 step 4: an agent's environment is built from nothing.
3. **A deploy mid-run: the container keeps running; the agent object doesn't.**
   - With Atlas's scheduling (`durable_object`), a deploy restarts every Durable Object, drops its WebSockets and loses what was in memory, but a running container keeps running, with its files and processes, on the image it started with ([sandbox lifetime](https://developers.cloudflare.com/sandbox/concepts/lifetime/), [WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). There's no hook before a stop.
   - So the bridge in the container keeps the agent running across a deploy, and the core reconnects to it. When the container itself was lost (a host restart, running out of memory), the job starts a new container from its branch and the agent's folder, and loads the session.
   - After a restart the `Workspace` object has no inactivity timeout until it sets one again; it already does in its constructor.
   - Code running inside a container isn't activity: with no requests it stops at the inactivity timeout, mid-build or not. A wake on the clock while the job runs keeps it up (§2 step 3).
4. **Git through the gate: Basic for git, bearer for the API.** GitHub takes a token for git over HTTPS as `Authorization: Basic` with `x-access-token:<token>` (what `actions/checkout` sends); its docs only document a bearer token for the REST API, and a bearer token for git has been reported refused. A fine-grained token needs Contents (write), Pull requests (write) and Metadata (read), plus Workflows (write) if a job may change `.github/workflows`. Checked for real by the first clone.
5. **The container's size: at least `standard-1` for a job.** Under Atlas's scheduling, `start()` takes `lite` (256 MB of memory) unless told otherwise, or `standard-1` to `standard-4`; running out of memory restarts the container and loses its disk ([limits](https://developers.cloudflare.com/containers/platform/limits/)). The workspace asks for `basic`, which the docs no longer list, so what it actually gets is read on the deployment. Cloudflare's own coding-agent runner uses `standard-1` (half a vCPU, 4 GB). An hour costs about $0.04 to $0.07 on `standard-1` and $0.06 to $0.13 on `standard-2`, before Workers Paid's included amounts ([pricing](https://developers.cloudflare.com/containers/platform/pricing/)); Jobs shows it.

## 6. Found while building

- **Four reviews, by area, changed the design, not just the code.** The first design ran the coding agent as root beside Atlas's own git commands, so an agent steered by a repo's contents could have read git's nonce from a command line and reached the owner's GitHub token. The fix was a model, not a patch: the agent is a stranger with its own Linux user, every command on its work runs as that user, keys are scoped to one repo and never on a command line, and root only touches the job's work as data (§4 decisions 9 to 11).
- **Fakes hide the gate.** The tests' fake workspace skips the network gate, so the first real clone was refused at github.com (Atlas's own git step carried the key but didn't open the site). A command that carries a key now opens its site while it runs, and a test covers the gate's decision.
- **A refusal with no words costs a round trip.** GitHub answered the next clone with a bare 429. The gate now keeps what it did and what the site said (status, words, rate-limit headers) and puts it in the error; after that deploy the clone went through, so the 429's cause wasn't seen.
- **One long helper per job was the wrong shape.** Waiting on an agent for an hour inside a helper's tool call would hold a fiber and a brain budget open; a short look per turn, with the job's state in the agent object, waits for free and survives anything.
- **The owner's words must never queue behind a long step.** Answers, settled approvals and Stop are written down at once and taken by the job's next wake.
- **Background work outlives a test.** A failed job's report, still running after its test ended, took the next test's scripted answer; tests now wait for what they start.
