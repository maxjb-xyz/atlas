# M7: launch

**Status:** open. The smoke test (§1) was written before the build (VISION rule 7), from the draft in [HANDOFF-M7.md §6](HANDOFF-M7.md#6-a-first-draft-of-m7s-smoke-test) and the owner's choices of 2026-10-24 (§3). M7 is built in stages; each stage closes when its part of the smoke test passes on the owner's deployment, and the milestone closes with the last. **Stage 1 (the look) closed on 2026-10-24** with the owner's approval of the mockups (docs/ui §8).

M7 proves **someone else can install it and love it** (VISION §25). Before a public release, the app has to meet two bars, simplicity and Jarvis, and it has to do what people will compare it with Hermes and OpenClaw on. So beside the launch work HANDOFF-M7 planned (setup steps 6 and 7, moving in, all themes, ambient mode, docs, the deploy button and a release), M7 adds, all decided with the owner on 2026-10-24:

- **the new places and settings** (VISION §21.2): People and Abilities in the sidebar, Atlas settings down to five sections, services as cards, a live map of what Atlas can do, and every record clickable;
- **releases and updates** (§23.2): one-click update and rollback from the Updates page;
- **brains** (§18): Anthropic by API key, named brains for kinds of work, and what a job does when its brain runs out;
- **abilities** (§9.3, §17): one catalog of services from an index, extension tools, and skills learned by a review after each conversation;
- **jobs Atlas owns** (§8.3): any long piece of work, with checkpoints with the owner;
- **reach** (§12.3, §14, §16.1): where a message Atlas starts goes, the owner's own permission rules, and phone calls through Telnyx;
- **what Cloudflare can see** (§20): Atlas's own encryption of the vault and keys, and plain words about it in the docs.

**Exit:** every stage's part of the smoke test passes on the owner's deployment, then M6's carried steps and the earlier lists; then someone other than the owner installs Atlas from the README alone.

## 1. The smoke test

Run each stage's part on the owner's deployment when that stage is built, and again after every deploy that touches it. When a line doesn't just work, the fix goes in the character, the context, a tool's description or the tool (rule 1), and the finding goes in this doc.

### Stage 1: the look

1. Mockups of the changed screens are in [docs/ui/](ui/README.md), drawn in the locked visual language, in dark and light: the sidebar with eight places, Abilities (the map, Services, a service opened, Skills, Devices), People (Contacts, Members, Faces), and Atlas settings' five sections (Atlas, Brains, Notifications, Permissions, Account). The owner has approved them, and the approval is written in docs/ui's README with the date. (This stage's check is the owner's OK, not the deployment.)

### Stage 2: groundwork

2. M6's carried steps ([M6.md §8](M6.md#8-carried-into-m7)) have been run with the owner, and what they found is fixed or written down here.
3. On a fresh Cloudflare account, the README's "Deploy to Cloudflare" button deploys Atlas with nothing else done by hand, and the app opens. What a new account needs turned on (Workers Paid, Containers, R2, Workers AI) is in the README, and the workspace deploys or the README says exactly what to do.
4. A tagged release builds the bundle and the Mac app. On the deployment, Atlas settings → Account → Updates shows the new version and its notes the day it's published; Update installs it in one click, with no terminal and no GitHub; Roll back brings the previous version back, and the data is all still there.
5. The vault and every stored key and token are encrypted by Atlas with the deployment's own key: an export of the agent's storage shows none of their values, and everything still works after a deploy.

### Stage 3: the new app

6. The sidebar has Home, Inbox, Agenda, then Automations, Library, People, Abilities, then History, with Pinned and Atlas settings. It matches the approved mockups in both themes, and the phone's tab bar keeps Home, Inbox, Agenda and Library with the rest under More.
7. Atlas settings has five sections. Nothing in them is a browser default control, no model is a typed id, and no control has more than a sentence under it. The composer never covers the bottom of a page.
8. Abilities opens on the map: every brain, sense, channel, hand, tool, skill and device Atlas has, each with what fills it, its state and its cost, and each box opens where it's set up. "What can you do?" puts the map on the stage.
9. Abilities → Services shows a card per service. Opening one shows what Atlas hears from it, what it can do there, what it can touch, its last error in the service's own words, and Off and Remove.
10. People → Faces has each face, its conversations and its "talk to it as a stranger" test; People → Members invites a member; People → Contacts lists the people Atlas knows.
11. Every record in Library, People and History opens on the stage when clicked.
11a. Simple is the default detail level: no model id, speed or price per token shows until "Show details". Outside services show their real logos. Now shows the diamond, the real mark in ember, moving (a sweep while idle; ripples, shimmer and pulse in voice), what's next on a small map with when to leave, and the weather. Picking Keyframes turns the stage's rails amber. People with a photo in the address book show it.
11b. In Library → Areas, the owner changes an area's color (a deep preset or any color) and its icon (a line icon, or a logo they upload). The chips, avatars, the week's load and the scoped stage change with it, everywhere, at once.

### Stage 4: brains

12. Atlas settings → Brains takes an Anthropic API key, tests it live, and lists Anthropic's models from its catalog with their speed and cost. With Anthropic first in the main chain, a conversation works end to end, and a second turn reads the stable part of the prompt from cache (the receipt at the Developer level shows it).
13. The owner names two brains, "Quick" and "Deep", each with a line on what it's for, and sets the defaults: helpers on Quick, research and a job's looks on Deep. "Compare these five laptops" starts helpers on Quick; the job shows which brain each used.
14. With the ChatGPT plan's limit hit partway through a long job, the job pauses at a clean step and asks in Inbox: wait until the limit resets (with the time), or go on with Anthropic (with what it would cost so far). Waiting resumes it at the reset; going on resumes it on Anthropic. Unanswered, it waits and spends nothing.

### Stage 5: abilities

15. Abilities → Services lists the catalog from the index: what's on, what's available, and Custom. Linear is one card that says what Atlas hears ("issues assigned to you, mentions") and what it can do ("create and update issues, comment"), with one setup.
16. "When a client emails about a bug, file it in Linear" makes an automation; the next such email files an issue through Linear's MCP server, asking the first time, with the issue linked in the receipt.
17. Custom adds an MCP server by its address and an extension from a link, each showing what it can touch before it's installed.
18. An extension from the index with a tool (a declared kind of "changes your things") runs without asking and offers Undo; one that "speaks to other people" asks until trusted.
19. After a conversation where the owner corrected how Atlas did something ("don't put the budget in the subject line"), the review that runs once the conversation goes quiet patches the skill that was used, and "Improved a skill" appears with Undo. A conversation with nothing worth keeping changes no skill.
20. Asked to save a skill that reads like one it already has, Atlas patches that one instead.
21. A skill folder from a skill hub (with `scripts/` and `references/`) installs from the catalog unchanged, its script runs in the workspace, and Download gives the folder back.

### Stage 6: jobs Atlas owns

22. "Make a 60-second launch video for Atlas" starts a job: Atlas makes a plan with its checkpoints ("approve the script", "approve the cut"), shows it in Jobs, and starts on it. The toolbar shows the job; Agenda lists it.
23. The script reaches the owner as a checkpoint in Inbox. Their edits go back into the job, which carries on from there.
24. The video's steps run as a coding job on a video project in the workspace, plus a voiceover from Atlas's own voice. The cut reaches the owner as the next checkpoint, playable on the stage.
25. The finished video lands in Library as a file, with a receipt, and the result in Inbox. Jobs shows what it cost and which brains did what.
26. A deploy mid-job, and a day's wait on a checkpoint, cost nothing while waiting and lose nothing.

### Stage 7: reach

27. With the app closed, something soon goes to the first channel on the owner's "soon" list (Telegram), something now to the "now" list, and something later into the next brief. Reading it on one device clears it on the others.
28. With the owner replying on Telegram a minute ago, Atlas's next message goes to Telegram whatever the lists say. A job's result goes back where the job was asked for.
29. Something urgent left unseen moves down the "now" list, ending with a phone call when that's allowed.
30. Atlas settings → Permissions changes "websites the workspace reaches" to any site; the next new site isn't asked about. Money and things that can't be undone can't be lowered there.
31. Abilities → Services → Telnyx takes one API key, lists the account's existing numbers with what each is connected to, and uses one: only that number's voice moves to Atlas, the account's other apps and numbers are unchanged, and "Give the number back" restores it. With no number, it offers one to buy, with its monthly price first.
32. The test call rings the owner's phone, and Atlas talks with the same mind and tools as in the app. The owner calling the number gets Atlas; another number gets the face.

### Stage 8: launch

33. Setup, from the passkey to Atlas saying something useful about the week, takes under 10 minutes on Workers AI alone, with no terminal. Every step can be skipped and picked up later; a failing check gives a plain reason and a fix there.
34. The first useful act goes through a real approval; the default routines are offered, each with its time.
35. Nothing optional bills before it's turned on: the account's usage after setup shows no container, phone number or paid provider.
36. A ChatGPT export and a Claude export import from setup's last step or Library: Atlas says where to get each, takes the file, and shows what it learned, each item to keep or drop. A Hermes or OpenClaw memory file imports the same way, and their skills carry over unchanged.
37. Each built-in theme (Graphite, Daylight, Terminal, Midnight, High contrast) renders every place and stage view, and the contrast check passes in `npm run check`. The owner's tweaks and a custom theme file apply live and follow the system's light or dark setting.
38. Ambient mode runs full screen on a tablet on a stand and keeps "now" current all day, as drawn. Media and the 3D model views render on the stage, as drawn.
39. The README and docs let a stranger deploy and set up Atlas, say what each optional piece costs, and say plainly what Cloudflare and each model provider can see (VISION §20).
40. The voice latency targets (VISION §11.2) are met on real calls, or the release notes say plainly that they aren't yet, with the numbers.
41. Someone other than the owner installs Atlas from the README alone.

## 2. The plan

Stage by stage, in order. Each stage starts with what's in §4 for it, and ends with its smoke test on the deployment. Keep the invariants: one loop, one log, one clock, one way out, one intake. Nothing tied to one service in the core.

**Stage 1: the look.** Mockups in the design canvas format (`docs/ui/source/`, built by `docs/ui/source/builder/`): the shell with eight places, then Abilities, People and the five settings sections, in dark and light. Reviewed with the owner and changed until approved; then docs/ui's README records what changed from UI v1.

**Stage 2: groundwork.**
- Run M6's carried steps with the owner; fix what they find.
- The deploy button, tried on a fresh Cloudflare account, with what the account needs written in the README.
- Releases: a workflow that builds the bundle (the Worker and the app) on a published release and attaches it beside the Mac app. Updates: a look on the clock once a day at the releases, the Updates page, and update and rollback through Cloudflare's API with the token from setup. A check in `npm run check` that a storage change only adds.
- Encryption: one key, a Worker secret made at deploy, wrapping the vault and every secret in `core/src/store/settings.ts`; existing values are encrypted on the first start after the update.

**Stage 3: the new app.** Build the approved mockups, with Simple as the default detail level, real logos for outside services and area colors as described in docs/ui §8; Home's Now with the living diamond (from `docs/ui/source/diamond.html`), the map to what's next and the weather; the stage's rails tinted by the scoped area; people's photos from the address book; each area's color and icon, which the owner picks (a deep preset or any color; a line icon or an uploaded logo in R2), with the eight presets in `app/` moved from pastels to the deep set in docs/ui §5; the shell's places, People, Abilities with the map (from what's installed, its state and cost), services as cards over today's extensions and MCP servers, the five settings sections, the app's own controls, every record opening on the stage, and the bugs found on 2026-10-24 (the composer covering the page's bottom, "Your data" always looking selected, the version label). `app/src/Settings.tsx` (3,250 lines) splits by place.

**Stage 4: brains.**
- An Anthropic provider (Messages API through AI Gateway, streaming, tool calls, prompt caching on the stable block) beside `core/src/brains/chatgpt.ts` and `workers-ai.ts`; `BrainChoice` gains it.
- Named brains in settings (each a chain and a line), defaults per kind of work, and a `brain` choice on `delegate` (only names and lines in its schema). A job keeps its brain on its state.
- The pause: a plan's limit or the cap seen by the router becomes a job's saved pause with a question in Inbox; the answer is kept like trust.

**Stage 5: abilities.**
- Each extension's manifest and each catalog entry carries its icon (the service's own logo, under its terms), shown on its card and on the map.
- The index: its format, a first index in its own repo (to be named), a snapshot in each release, the daily look, and Custom. Services as one catalog entry over an extension, an MCP server and skills.
- Extension tools: `tools` in the manifest, each with its kind and input schema, offered to the model like any tool and run in the sandbox; the outbox and approvals treat them by their kind.
- Skills: the review after a conversation goes quiet (an agenda item, one of Atlas's own runs, only the skill tools); targeted patches in `skill_save`; the near-duplicate check by embeddings; folders in R2; merging in the nightly tidy; reuse counted.

**Stage 6: jobs Atlas owns.** The coding desk's way of working (`core/src/agent/coding.ts`) made general: a goal record, a plan with checkpoints, a folder in the workspace, a budget, short looks on the clock, helpers with powers scoped to the job, results as files and pages. A coding step stays a coding job.

**Stage 7: reach.**
- Urgency (now, soon, later) on what Atlas says on its own; the outbox's order (where you're talking, where it started, your list); lists per urgency; escalation; suggestions from reactions.
- Permissions: the kinds and the named rules as settings, with their floors in code (`core/src/approvals.ts`).
- Telnyx as an extension that provides a channel for calls: the API key, the account's numbers, using one (Atlas's own voice app, only that number's voice moved, the old connection kept for "Give the number back"), buying one, a test call; calls stream audio to the person agent's voice pipeline while live.

**Stage 8: launch.** HANDOFF-M7's steps 3 to 7: setup steps 1 to 7 timed from a fresh account, moving in (readers as extensions, the extraction the core's), all themes and the contrast check, ambient mode and the last views (each with its design pass first), the docs, and a public release.

**Reviews:** each stage gets reviewed by area before its smoke test, as M6 did. The catalog, extension tools and Telnyx each touch the gate or the exits, and get a security review of their own.

## 3. Decisions

Made with the owner on 2026-10-24; each is in VISION in its own commit:

1. **Skills** are learned mostly by a review after each conversation, on the clock, with only the skill tools; near-duplicates are refused; skills are folders (VISION §9.3).
2. **Extension or MCP:** extensions for what the core needs (hearing from a service, providers it picks between, file readers, tools for a service with no MCP server); MCP for a vendor's own tools. **One catalog of services**, one card each, from an index file pinned by hash; Custom for anything else. No hooks into the loop (§17).
3. **Jobs Atlas owns** any long work, with checkpoints with the owner (§8.3).
4. **Brains:** Anthropic by key first; named brains for kinds of work, picked by name only; a job pauses and asks when its brain runs out (§18).
5. **Permissions** the owner can change, within fixed floors (§12.3).
6. **Where messages go:** Atlas sets urgency; the outbox picks the channel by where the owner is talking, where it started, then their list per urgency (§14).
7. **Phone calls through Telnyx,** voice only, with existing accounts and numbers welcome. WhatsApp waits (§16.1, §26 item 5).
8. **Encryption:** Atlas's own key for the vault and keys, and plain words about what Cloudflare can see. Passkey-sealed entries later (§20).
9. **Updates:** release bundles, one-click update and rollback; storage changes only add (§23.2).
10. **The UI:** eight places with People and Abilities, five settings sections, services as cards, the map (§21.2). The look is redone where it doesn't meet simplicity and Jarvis.
11. **A picture of your life** (export readers, live feeds, About you) is put off; M7 keeps getting more from what Atlas already sees (§5.1, §27).
12. **Moving in** stays in M7.

## 4. Verify first

Before each stage's build, check what it depends on, against the real service where possible:

- **Stage 2:** whether the deploy button provisions Containers (its docs list Durable Objects, R2 and Workers AI, but not Containers); which permissions the Cloudflare token needs to upload a version and roll back; whether a Durable Object migration can ride in a version upload, or a release with one needs a full deploy through the API (and so can't be rolled back past).
- **Stage 4:** Anthropic through AI Gateway with streaming, tool calls and cache control; how a plan's limit shows in ChatGPT's responses (its reset time), so a pause can say when.
- **Stage 5:** fetching the index and pinned files from GitHub inside the Worker; how Linear's MCP server takes a Linear API key, so one key covers both parts; a similarity threshold for near-duplicate skills that holds on real skills.
- **Stage 7:** Telnyx's two-way media streaming into a Durable Object (its audio format, and what speech in and out need for it); moving one number's voice to a new app by API and restoring it; how Telnyx's webhook signature is checked and where its key comes from.
